# 🖥️ Server Monitoring Telegram Bot (`bot-fiz`)

Модульный Telegram-бот на Java для оперативного удалённого мониторинга серверной инфраструктуры, контроля системных ресурсов (CPU, RAM, Disk) и проверки доступности сетевых сервисов.

Проект спроектирован с упором на чистую архитектуру, слабую связность компонентов (*Loose Coupling*), расширяемость функционала и соблюдение практик безопасной разработки (*Security by Design*).

## 📌 О проекте

При администрировании небольших серверов, VPS, лабораторных стендов и пет-проектов развёртывание тяжеловесных систем мониторинга (связки *Prometheus + Grafana*, *Zabbix*, *ELK-стек*) зачастую избыточно: они требуют выделенных вычислительных ресурсов, сложной настройки и постоянного обслуживания.

**`bot-fiz`** решает задачу **легковесного и оперативного мониторинга**:
* **Мгновенный доступ:** администратор запрашивает статус сервера и метрики напрямую через интерфейс Telegram без необходимости ручного подключения по SSH.
* **Минимальное потребление ресурсов:** приложение работает в рамках одного легковесного JVM-процесса.
* **Простая расширяемость:** модульная структура позволяет добавлять новые метрики и проверки за считанные минуты.
* **Проактивный контроль:** архитектура закладывает возможность отправки автоматических уведомлений (алертов) при критической нагрузке на узлы.

## 🏗 Архитектура и принципы проектирования

Архитектура приложения разделена на независимые функциональные слои, что исключает жёсткую привязку бизнес-логики к внешнему API мессенджера:

```text
[ Telegram Bot API ]
         │
         │ (Long Polling / JSON Updates)
         ▼
[ TelegramBot Adapter ] ─── (Сетевой транспорт: OkHttpTelegramClient)
         │
         │ (Извлечение и передача сырого текста сообщения)
         ▼
[ CommandHandler ] ──────── (Диспетчер и маршрутизатор команд)
         │
         │ (Парсинг аргументов и поиск в реестре Map<String, Command>)
         ▼
┌─────────────────────────────────────────┐
│           Интерфейс «Command»           │  <── Паттерн «Команда» (Command Pattern)
└────────────────────┬────────────────────┘
                     ├── AboutCommand     (/about)
                     ├── AuthorCommand    (/author)
                     ├── HelpCommand      (/help, /help <cmd>)
                     ├── RamCommand       (/ram)      ──► [SystemMetricsService]
                     ├── CpuCommand       (/cpu)      ──► [CpuMonitorService]
                     ├── UptimeCommand    (/uptime)   ──► [CpuMonitorService]
                     └── StatusCommand    (/status)   ──► [Агрегация метрик CPU, RAM, Disk, Uptime]
```

### Ключевые архитектурные решения

1. **Паттерн «Команда» (Command Pattern):**
   Каждая команда бота инкапсулирована в отдельный класс, реализующий единый контракт `Command`. Это обеспечивает соблюдение принципа открытости/закрытости (*Open-Closed Principle, SOLID*): для добавления новой команды достаточно создать новый класс и зарегистрировать его в диспетчере, не изменяя код существующих команд.
2. **Изоляция транспортного уровня (Decoupling):**
   Классы бизнес-логики (`CommandHandler`, сервисы метрик и реализации `Command`) не зависят от библиотеки `TelegramBots`. Они принимают на вход обычные строки (`String`) и возвращают текстовый результат. Сетевой слой (`TelegramBot`) выступает исключительно в роли адаптера.
3. **Высокая тестируемость (Testability):**
   Благодаря отделению логики от транспортного слоя и инъекции сервисов через конструкторы, тестирование маршрутизации, расчёта метрик и генерации ответов выполняется чистыми JUnit-тестами за миллисекунды — с использованием стабов и без поднятия сетевых соединений.
4. **Безопасность по умолчанию (Security by Design):**
   В кодовой базе и конфигурационных файлах репозитория строго запрещено хранение чувствительных данных. Токен авторизации бота считывается исключительно из переменных окружения операционной системы (`System.getenv("BOT_TOKEN")`).

## ⚡ Доступные команды

| Команда | Аргументы | Описание |
| :--- | :---: | :--- |
| `/help` | — | Выводит полный список зарегистрированных в системе команд с их кратким описанием |
| `/help <command>` | `имя_команды` | Выводит детальную справку по конкретной команде (с лидирующим слэшем или без него) |
| `/about` | — | Отображает информацию о назначении бота, его функциональности и концепции |
| `/author` | — | Выводит информацию об авторах и разработчиках проекта |
| `/ram` | — | Показывает статистику использования физической памяти (ОЗУ) и раздела подкачки (Swap) |
| `/cpu` | — | Выводит количество доступных ядер, общую загрузку CPU, нагрузку процесса бота и Load Average |
| `/uptime` | — | Показывает время непрерывной работы процесса бота (JVM) и операционной системы сервера |
| `/status` | — | Выводит сводный дашборд состояния сервера (CPU, RAM, Swap, Disk, Uptime) с прогресс-барами |

**Цель:** Заложить расширяемую архитектуру на базе паттерна *Command* и подключить Telegram API.

- [x] **Задача 1.1. Архитектурное ядро и CLI-режим**
  - **Что нового:** Интерфейс `Command`, маршрутизатор `CommandHandler`, базовые команды `/about`, `/author`, `/help`.
  - **Результат:** Работающий в консоли прототип, покрытый базовыми unit-тестами `CommandHandlerTest`.
- [x] **Задача 1.2. Интеграция с Telegram Bots API (Long Polling)**
  - **Что нового:** Сетевой адаптер `TelegramBot`, подключение `telegrambots-longpolling` и `telegrambots-client`, безопасное чтение токена через переменную окружения `BOT_TOKEN`.
  - **Результат:** Бот принимает команды и отвечает пользователям в реальном времени через Telegram.

## Этап 2. Локальный мониторинг ресурсов сервера (Host Metrics) (Выполнено)
**Цель:** Научить бота собирать аппаратные метрики машины, на которой запущен JVM-процесс, без использования сторонних консольных утилит.

- [x] **Задача 2.1. Мониторинг оперативной памяти (`/ram`)**
  - **Что нового:** Сервис `SystemMetricsService` (`DefaultSystemMetricsService`) на базе `OperatingSystemMXBean`, модель `RamMetrics` + класс `RamCommand`.
  - **Функционал:** Вывод общего, занятого и доступного объема ОЗУ и Swap (в МБ/ГБ и процентах).
  - **Тесты:** Проверка корректности расчета занятой памяти, процентов и обработки пограничных значений (`RamCommandTest`).
- [x] **Задача 2.2. Мониторинг нагрузки процессора и аптайма (`/cpu`, `/uptime`)**
  - **Что нового:** Сервис `CpuMonitorService` + команды `CpuCommand` и `UptimeCommand`.
  - **Функционал:**
    - `/cpu`: текущая загрузка CPU в процентах (`getCpuLoad()`), нагрузка процесса JVM, количество доступных ядер и Load Average.
    - `/uptime`: время непрерывной работы сервера (`/proc/uptime`) и самой JVM.
  - **Тесты:** Unit-тесты нормализации нагрузки и парсера времени в формат `X дн. Y ч. Z мин. W сек.` (`CpuMonitorServiceTest`, `CpuAndUptimeCommandsTest`).
- [x] **Задача 2.3. Мониторинг дискового пространства (`/disk`)**
  - **Что нового:** Анализ файловых хранилищ на базе `java.nio.file.FileStore`.
  - **Функционал:** Анализ основного раздела, вывод общего объема, занятого места и процента заполнения.
  - **Тесты:** Проверка форматирования объемов накопителя и расчета процента заполнения.
- [x] **Задача 2.4. Сводный дашборд состояния (`/status`)**
  - **Что нового:** Агрегирующая команда `StatusCommand`, объединяющая данные из сервисов CPU, RAM, Disk и Uptime в единый компактный отчет с визуальными прогресс-барами.
  - **Функционал:** Быстрая сводка здоровья сервера одним сообщением (`StatusCommandTest`).

## Этап 3. Мониторинг процессов, служб и сети (System & Network Checks)
**Цель:** Добавить контроль за внешними узлами и системными демонами ОС с соблюдением практик безопасного вызова процессов.

- [ ] **Задача 3.1. Сетевой чекер доступности портов и хостов (`/check <host> <port>`)**
  - **Что нового:** Сетевой сервис `NetworkCheckService` на базе `java.net.Socket` с жестким таймаутом подключения + команда с поддержкой аргументов `CheckCommand`.
  - **Функционал:** Проверка доступности TCP-порта на указанном хосте (например, `/check 127.0.0.1 5432` или `/check google.com 443`) и замер времени отклика в миллисекундах (RTT).
  - **Тесты:** Валидация входных аргументов (IP/домен, диапазон портов 1–65535), защита от некорректного ввода.
- [ ] **Задача 3.2. Безопасный контроль системных служб (`/service <name>`)**
  - **Что нового:** Исполнитель системных вызовов через `ProcessBuilder` с белым списком (whitelist) разрешенных имен сервисов + команда `ServiceCommand`.
  - **Функционал:** Проверка статуса критических демонов (`nginx`, `postgresql`, `docker`, `ssh`) через `systemctl is-active`. Строгая валидация имени сервиса по регулярному выражению `^[a-zA-Z0-9_-]+$` для предотвращения *Command Injection*.
  - **Тесты:** Тестирование фильтра безопасности на попытки инъекций (например, `/service nginx; rm -rf /` должен жестко блокироваться).

## Этап 4. Безопасность и контроль доступа (Security & Auth)
**Цель:** Закрыть приватные метрики сервера от посторонних пользователей Telegram.

- [ ] **Задача 4.1. Авторизация по White-листу (`Admin Filter`)**
  - **Что нового:** Модификация контекста выполнения команд (передача `chatId` / `userId`), чтение списка разрешенных ID администраторов из переменной окружения `ADMIN_IDS`.
  - **Функционал:** Разделение команд на публичные (`/help`, `/about`, `/author`) и приватные (`/status`, `/ram`, `/cpu`, `/disk`, `/service`, `/check`). Посторонним пользователям возвращается отказ в доступе с логированием попытки.
  - **Тесты:** Проверка прохождения команд для разрешенного `userId` и блокировки для неавторизованного.

## Этап 5. Автоматический мониторинг и система уведомлений (Alerting)
**Цель:** Перевести бота из режима «вопрос-ответ» в режим проактивного сторожа, который сам пишет админу при авариях.

- [ ] **Задача 5.1. Фоновый планировщик пороговых значений (`AlertScheduler`)**
  - **Что нового:** Фоновый поток на базе `ScheduledExecutorService` и команда настройки/просмотра порогов `/alerts`.
  - **Функционал:** Опрос CPU, RAM и диска каждые $N$ секунд. Если нагрузка превышает порог (например, RAM > 90% или Disk > 95%), бот сам отправляет экстренное уведомление всем `ADMIN_IDS`. Добавление механизма *cooldown* (чтобы бот не спамил каждую секунду при затяжной нагрузке).
  - **Тесты:** Тестирование логики срабатывания триггеров и подавления повторных алертов (cooldown).

## Этап 6. Деплой и контейнеризация (DevOps)
**Цель:** Упаковать приложение для запуска на реальном Linux-сервере в одну команду.

- [ ] **Задача 6.1. Сборка fat-JAR и Docker-образ**
  - **Что нового:** Настройка `maven-shade-plugin` в `pom.xml`, создание многоступенчатого (multi-stage) `Dockerfile` и `docker-compose.yml`.
  - **Функционал:** Автоматическая сборка независимого архива и запуск бота в изолированном контейнере с пробросом переменных окружения (`BOT_TOKEN`, `ADMIN_IDS`).

## Распределение ролей и правила работы (Workflow)
1. **Ветвление:** Под каждую задачу (`2.1`, `2.2` и т.д.) создается отдельная ветка от `main`: `feature/task-2.1-ram-command`.
2. **Критерий готовности (Definition of Done):**
- Код компилируется без ошибок и предупреждений.
- Написаны модульные тесты (JUnit 5), `mvn clean test` проходит успешно.
- Команда автоматически отображается в `/help`.
- Проведено код-ревью вторым участником команды (Вадим ↔ Егор) через Pull Request перед слиянием в `main`.

## 🚀 Быстрый старт

### Предварительные требования
* Установленный **JDK** версии **17** или **21** (`java -version`).
* Установленный **Apache Maven** версии **3.8+** (`mvn -version`).
* Зарегистрированный Telegram-бот и полученный API-токен от [@BotFather](https://t.me/BotFather).

### 1. Клонирование репозитория
```bash
git clone https://github.com/GoodyYam/bot-fiz.git
cd bot-fiz
```

### 2. Настройка переменных окружения
Перед запуском необходимо передать токен бота через переменную окружения `BOT_TOKEN`:

* **Linux / macOS (Bash / Zsh):**
  ```bash
  export BOT_TOKEN="123456789:ABCdefGhIJKlmNoPQRsTUVwxyZ"
  ```
* **Windows (Command Prompt / CMD):**
  ```cmd
  set BOT_TOKEN=123456789:ABCdefGhIJKlmNoPQRsTUVwxyZ
  ```

## 🧪 Тестирование

В проекте используется фреймворк **JUnit 5 (Jupiter)**. Модульные тесты расположены в пакете `src/test/java/org/example/` и проверяют:
* **`CommandHandlerTest`**: корректность маршрутизации базовых команд (`/about`, `/author`, `/help`), работу детализированной справки `/help <command>` и обработку невалидного ввода;
* **`RamCommandTest`**: корректность расчёта занятой физической памяти и Swap, вычисление процентов и форматирование отчёта команды `/ram`;
* **`CpuMonitorServiceTest` и `CpuAndUptimeCommandsTest`**: нормализацию показателей загрузки CPU, обработку недоступных метрик (`-1.0`, `NaN`), парсинг системного аптайма Linux (`/proc/uptime`) и форматирование интервалов времени для `/cpu` и `/uptime`;
* **`StatusCommandTest`**: корректность агрегации всех метрик в единый дашборд `/status`, генерацию текстовых прогресс-баров и перевод байтов в МБ/ГБ.

Запуск тестового набора:
```bash
mvn test
```
